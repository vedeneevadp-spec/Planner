# Выпуск и откат удаления встроенного ввода

Этот документ — план. Production-деплой, рабочая БД, внешние кабинеты,
ключи, account links и публикация APK в ходе реализации не изменялись.

## Обязательное разделение выпуска

`scripts/deploy-prod.mjs` применяет миграции **до** переключения API и при
ошибке может вернуть предыдущий release. Старый API читает удаляемые
столбцы. Поэтому прямой выпуск финального дерева поверх старого backend
небезопасен; автоматический возврат старого кода после 000106 не является
рабочим откатом.

Подготовить два проверенных релизных состояния, не переписывая ранее
применённые миграции:

1. **Переходный релиз A:** новый API/web без встроенного ввода и с wire
   adapter `false`, но без новых миграций 000106/000107 в пакете миграций.
   Это отдельное явно оформленное состояние исходников для выпуска.
   API использует только сохраняемые поля и работает на схеме до 000106.
2. **Финальный релиз B:** тот же совместимый API/web плюс 000106 и 000107.
   Предыдущим release для автоматического rollback должен быть A.

Не удалять миграции из уже выпущенного артефакта вручную и не обходить
checksum/lock проверки. Для A и B нужны отдельные review и release refs.
В этой задаче эти production refs не создавались. Совместимость нового
кода со старой схемой 000105 подтверждена 94 PostgreSQL-тестами и
реальными HTTP/settings/backup проверками:
[transition-verification.md](transition-verification.md).

## Последовательность

1. Перед выпуском устранить или явно разобрать исходные ошибки общего
   web-test/lint gate из отчёта. Проверить обновление APK на тестовом
   устройстве с включённым старым помощником, активной сессией, виджетом,
   офлайн-очередью и ожидающей голосовой командой.
2. Снять обычный инфраструктурный backup; проверить восстановление
   SQL dump в изолированную БД и применение всей цепочки новых миграций.
   Сохранить артефакты и контрольные суммы релизов A/B.
3. Выпустить A штатным guarded workflow. Проверить health/readiness,
   обычный вход/refresh/выход, настройки, задачи, покупки и workspace.
   `/api/voice/command` и `/api/voice/metrics` должны возвращать 404.
   Session и preferences должны возвращать старым клиентам голосовые
   значения `false`, даже после PATCH с `true`.
4. Обновить web/PWA. Убедиться, что активирован SW runtime cache v4,
   старые shell/chunks больше не используются, IndexedDB и очередь
   синхронизации сохранены, старый URL переводит на `/today`.
   Caddy должен отдавать `microphone=()`.
5. Собрать и выпустить подписанный APK с действующим applicationId,
   signing identity и production API URL. Проверенный здесь debug APK
   использует локальный тестовый API и **не предназначен для публикации**.
   Native cleanup выполняется до запуска bridge, не затрагивая auth и
   Keystore; проверить реальное открытие системных настроек уведомлений.
6. После подтверждения, что все API/worker/restore процессы используют
   совместимый код A, выпустить B. 000106 удалит только два столбца и
   голосовую перегрузку preferences; 000107 исправит исходную неоднозначность
   `id` в двух перегрузках обмена OAuth-кода Алисы.
7. Повторить runtime DB security/RLS, preferences и backup roundtrip;
   проверить source=`voice` в исторических покупках и новых покупках Алисы.

## Контрольные точки Алисы

- Сохранены `POST /api/v1/alice/webhook`, оба authorize routes и token route.
- В API-процесс переданы `ALICE_OAUTH_*`, `ALICE_LLM_*`, `YANDEX_API_KEY`,
  `YANDEX_FOLDER_ID`; токены и существующие account links не отзывались.
- На специально выделенном тестовом аккаунте: account linking, authorization
  code exchange, refresh, задача с датой/временем, покупка source=`voice`,
  получение плана, правила и LLM fallback.
- Отдельно проверить настоящий навык в Яндекс Диалогах. Локальные HTTP/SQL
  тесты не подтверждают прохождение этого внешнего сценария.

## Старые клиенты и срок адаптера

Адаптер возвращает `voiceAssistantEnabled=false` и
`wakeWordTrainingModeEnabled=false`; известные boolean-поля старых PATCH
принимаются и игнорируются. Остальные настройки сохраняются. Голосовых
сервисов за адаптером нет.

Удалять адаптер можно только после прекращения поддержки всех web/APK,
которые используют `default(true)`, включая сохранённые PWA shell, и
проверки согласованного нового OpenAPI. Дата удаления заранее не назначена.
Поддержка старых backup v1 сохраняется независимо от срока адаптера.

Уже установленный старый APK или открытая старая вкладка могут продолжать
исполнять свой локальный код до обновления/перезагрузки. Новый сервер не
обрабатывает их аудио; отключение локального runtime гарантируется новым
клиентом. Удалённо остановить произвольный офлайн-APK эта серверная миграция
не может. Этот промежуток закрывается процедурой обновления клиента.

## Секреты

После проверки внешних потребителей отдельно рассмотреть отключение
`VOICE_STT_YANDEX_API_KEY`, `VOICE_STT_YANDEX_ENDPOINT`,
`VOICE_STT_YANDEX_FOLDER_ID`, `VOICE_STT_YANDEX_IAM_TOKEN`,
`VOICE_STT_LANGUAGE`, `VOICE_STT_TIMEOUT_MS`. Передача `YANDEX_IAM_TOKEN`
также удалена: в репозитории он обслуживал только старый STT.

Значения реальных local/production env не удалялись. Не отзывать общие
`YANDEX_API_KEY`/`YANDEX_FOLDER_ID` или настройки Алисы. Имя переменной
само по себе не доказывает, что ключ не используется вне репозитория.

## Откат

- До 000106 схема прежняя; откат приложения технически возможен, но возврат
  версии со встроенным вводом восстановит удаляемую функцию. Предпочтителен
  исправляющий выпуск A.
- После 000106 безопасная кодовая точка отката — A: она не читает удалённые
  столбцы. Держать исправление OAuth 000107; оно не меняет сигнатуры/права.
- HEAD `2b40273` и более ранний backend нельзя просто вернуть на новую
  схему. Для него потребуются отдельная проверенная обратная миграция
  столбцов и старой трёхаргументной функции с grants/RLS. Такая обратная
  миграция не подготовлена и автоматически не выполняется.
- Значения удалённых voice-настроек после 000106 потеряны; актуальные задачи,
  покупки, профили, прочие настройки, сессии и OAuth links сохранены.
  Восстановление всей production БД из старого dump потеряет последующие
  записи и не является обычным откатом кода.
- Android: предпочтителен исправляющий APK с тем же signing identity и
  увеличенным versionCode; не очищать данные приложения. Личные samples
  сохранены, но новый клиент не имеет их загрузчика/исполнителя.
