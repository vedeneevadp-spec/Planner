## P1: исправить в первую очередь

### TD-01. Сохранение ритуала стирает подробную историю

**Сценарий.** Создать ритуал с шагом → выполнить шаг → сохранить тот же ритуал, передав тот же ID шага. В PostgreSQL число `self_care_ritual_step_completions` уменьшается **с 1 до 0**, хотя родительская запись выполнения остаётся. Это потеря сохранённых подробностей, а не только ошибка отображения.

**Причина.** [Репозиторий заботы](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care/self-care.repository.postgres.ts:398>) удаляет все шаги и вставляет их заново; отдельный путь `updateRitualSteps` повторяет это на строке 1746. [Внешний ключ истории](</Users/daryavedeneeva/ Projects  /Planner/db/migrations/20260606_000057_self_care.sql:186>) имеет `ON DELETE CASCADE`. [Форма ритуала](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/pages/self-care/ui/SelfCarePage.form-model.ts:820>) отправляет шаги при каждом сохранении: достаточно редактирования названия ритуала.

**Исправление.** Обновлять шаги по стабильным ID, явно обрабатывать добавление/удаление и сохранять исторические данные. Отдельно решить, должна ли история показывать прежнее название шага: для этого подходит снимок названия/порядка в записи выполнения. Уже удалённые подробности не восстановить из текущих таблиц без другого источника, например backup.

**Приёмка.** Переименование ритуала и шага, перестановка, добавление/удаление шагов сохраняют прежние результаты; новые выполнения используют новый состав. Повторный offline replay не удаляет и не дублирует историю.

### TD-02. Изменение расписания зависит от того, что пользователь раньше открывал

**Сценарий.** Создать daily 09:00 → открыть неделю 14–20 сентября → изменить правило на понедельники 12:00 → снова открыть неделю. Правило сохранено правильно, но **все семь созданных экземпляров остаются ежедневными в 09:00**.

**Причина.** [Сохранение правила](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care/self-care.repository.postgres.ts:2341>) обновляет rule; дальнейший код лишь связывает записи без rule ID. [Генератор](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care/self-care.shared.ts:688>) пропускает уже существующие даты. Пересогласования будущих scheduled occurrences нет. Изменение одного выбранного экземпляра в клиентской batch-операции не пересчитывает весь период.

**Исправление.** Ввести явную область изменения: «только этот раз» / «этот и следующие». В одной транзакции согласовывать незавершённые автоматически созданные будущие экземпляры и напоминания, сохраняя завершённую историю и ручные исключения.

**Приёмка.** Daily → weekly, изменение времени/часового пояса, конца повторения и отключение расписания дают одинаковый результат с ранее открытым календарём и без него. Отдельные ручные переносы и история не исчезают.

### TD-03. Повторяющиеся напоминания требуют предварительного чтения данных

**Сценарий.** Создать правило с временем и напоминанием в текущем окне доставки. Сразу после создания: **0 occurrences**, worker возвращает **0 reminders**. После чтения dashboard на соответствующую дату: worker возвращает **1 reminder**. Настоящие push не отправлялись.

**Причина.** [Создание заботы](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care/self-care.repository.postgres.ts:250>) сохраняет item/rule. Генерация запускается чтением dashboard/plan/history/analytics для запрошенных дат или явным API. [Worker repository](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care-reminders/self-care-reminders.repository.postgres.ts:183>) выбирает только существующие экземпляры. [Worker](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/workers/task-reminders.ts:40>) не генерирует недостающие повторы. Клиентский prefetch имеет конечный горизонт и не решает сценарий длительного отсутствия пользователя.

**Последствие.** После выхода за ранее сгенерированный период корректно настроенные напоминания могут перестать появляться. Наличие конкретных пропущенных production-уведомлений этим аудитом не установлено.

**Исправление.** Фоновая серверная генерация на скользящий горизонт с ограниченными batch, идемпотентностью и прогрессом обработки. Чтение может дополнять произвольные периоды, но не должно быть условием надёжности напоминаний.

**Приёмка.** После создания закрыть все клиенты, перевести тестовые часы за завтра и за первоначальный горизонт, запускать только workers: каждый ожидаемый повтор получает ровно одно своевременное напоминание. Проверить DST, смену правил и timezone.

### TD-04. Контракт native refresh реализован на Android, но отсутствует на iOS

[Общий storage-клиент](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/session/lib/auth-session-storage.ts:148>) вызывает `prepareRefresh` и `commitRefresh` на native-платформах. Подготовка выполняется [до HTTP refresh](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/session/lib/useSessionAuthController.ts:443>). Однако [Swift bridge](</Users/daryavedeneeva/ Projects  /Planner/ios/App/App/AppDelegate.swift:9>) экспортирует только `get`, `set`, `remove`; требуемых двух реализаций в tracked iOS-коде нет. Для доступности метода JavaScript нужны и реализация, и регистрация в `pluginMethods` — это соответствует [контракту Capacitor 8](https://capacitorjs.com/docs/plugins/ios#export-to-capacitor).

**Последствие по коду.** При необходимости обновить сохранённую iOS-сессию вызов не доходит до штатного HTTP refresh и превращается в retryable storage error; повтор не добавит отсутствующую реализацию. Воспроизведение на устройстве не выполнялось. P1 обоснован при заявленной в README поддержке iOS.

**Исправление.** Добавить эквивалентные атомарные prepare/commit операции Keychain и общий тест соответствия native API. Если iOS намеренно не поддерживается, явно обозначить это в продукте и release matrix.

**Приёмка.** На iOS: вход → истечение токена → автоматическое обновление; offline/reconnect; остановка процесса в середине ротации; поздний ответ параллельного refresh. Проверять настоящий bridge, а не только JS mock.

### TD-05. Голосовой preview не привязан к пространству исполнения

**DIAG.** Реальный executor подготовил команду в `personal-A`; подтверждение с текущим контекстом `shared-B` завершилось `success` и передало личное название в `shared-B.createTask`. API boundary моделировалась: реальные пользовательские данные никуда не отправлялись.

**Причина.** [Executor](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/voice-assistant/model/planner-action-executor.ts:206>) проверяет роли/блокировку/опасность, но не равенство actor/workspace сохранённого preview и текущего контекста. [Voice flow](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/voice-assistant/model/useVoiceActionFlow.ts:161>) использует новые session/dependencies. Компонент остаётся вне маршрутов и не сбрасывается по workspace.

**Условие UI.** Особенно важен переход в **ранее открытое и закэшированное** пространство: [initialData](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/session/lib/usePlannerSession.ts:78>) позволяет переключиться без промежуточного размонтирования. Для впервые открытого пространства загрузка может случайно скрыть проблему. Полный браузерный голосовой сценарий не проигрывался.

**Исправление.** Связать preview, undo и незавершённое распознавание с actor/workspace/generation. Сбрасывать preview при переключении и независимо отклонять несовпадение внутри executor. В подтверждении показывать пространство назначения.

**Приёмка.** Прогреть A/B → получить preview в A → перейти в B → подтвердить/отменить. Ни один вариант не пишет в B. Поздняя расшифровка и поздний ответ старого запроса также не меняют новое пространство.

### TD-06. Одна недопустимая операция удерживает всю очередь пространства

**DIAG.** В реальном store/drain с `fake-indexeddb` поставлены запрещённая задача, затем допустимая. После трёх попыток drain вызвана только первая — **3 раза**; вторая остаётся `pending`, `attemptCount=0`. Данные второй операции сохраняются, но до сервера не доходят.

**Причина.** [Классификатор](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/lib/offline-planner-sync.ts:454>) не относит реальные `task_status_forbidden`, `task_confirmation_required`, `task_manage_forbidden` к окончательным ошибкам команды. [Общий drain](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/shared/lib/offline-sync/offline-sync.ts:190>) помечает такую запись failed и прерывает обработку. Failed остаётся retryable с прежним порядком. Изменение назначения/роли во время offline — реальный путь к такой ошибке; permission check API идёт раньше проверки версии. Через эту очередь обычно проходят и online-изменения.

**Исправление.** Разделить восстановление авторизации, временную транспортную ошибку, конфликт версии и окончательный отказ отдельной команды. Сохранять ввод и показывать понятное действие для конкретной записи. Разрешать независимым задачам синхронизироваться, сохраняя зависимости операций одной цепочки.

**Приёмка.** Проверить 400, разные 403, 409, 429, 5xx и offline role/assignee change. Ошибка одной задачи не останавливает независимую следующую. Retry/discard не теряют ввод и не нарушают порядок зависимых create/update/next-stage.

### TD-07. Ограниченная выборка не везде имеет доступное продолжение

[CalendarPage](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/pages/calendar/ui/CalendarPage.tsx:711>) запрашивает cursor с `limit: 500`, но не использует `nextCursor`; banner лишь сообщает первые N из total. [Страница сферы](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/pages/spheres/ui/SpherePage.tsx:51>) фильтрует общий bounded snapshot без собственной пагинации. [Обзор сфер](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/pages/spheres/ui/SpheresPage.tsx:196>) считает наличие записей признаком полноты и строит статистику по ним. [Today](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/pages/today/ui/TodayPage.tsx:128>) называет active/range truncation «большим архивом» и обещает постраничную загрузку, которой для этих списков нет.

**Последствие.** Запись вне snapshot может отсутствовать в сфере, а статистика — выглядеть полной. Часть большого диапазона календаря может оказаться недоступной: записи, отсутствующие одновременно в первых 500 cursor и базовом snapshot. Само превышение 500 не гарантирует пропуска из-за объединения выборок. Это остаток прежнего TD-05, а не повтор закрытого бага изменения уже загруженной cursor-записи. **Исправление и приёмка.** Cursor/infinite loading по каждому необходимому scope, серверные агрегаты сфер или честная маркировка неполных метрик. На >500 active/range и >100 closed все подходящие записи достижимы, без дублей и неограниченного initial fetch. Пользовательский текст объясняет объём данных без термина «snapshot».

### TD-13. Два workers могут одновременно считать одно напоминание своим

**SQL.** Два последовательных `claimDueReminders(25)` без подтверждения доставки немедленно возвращают **один и тот же reminder ID**, хотя предусмотрен пятиминутный lease.

[Каждый claim](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care-reminders/self-care-reminders.repository.postgres.ts:28>) сначала запускает materialization; [ON CONFLICT](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care-reminders/self-care-reminders.repository.postgres.ts:264>) безусловно сбрасывает `claimed_at = null`. `SKIP LOCKED` защищает транзакцию, а отправка происходит позже. Локальный single-flight одного poller не защищает два процесса. На одном worker дубль этим сценарием не доказан; реальная доставка не выполнялась.

**Исправление и приёмка.** Не менять claim при неизменившемся расписании. Для изменённого — version/claim token, защита от старого ack. После claim A worker B не получает запись до ack/release/истечения lease; старый ответ A не помечает новую доставку завершённой.

## Что не нужно повторно исправлять

- Основной planner loader уже использует bounded read model. Прежняя неограниченная загрузка всех задач не является текущим выводом.
- Кэш задач уже синхронизирует загруженные cursor pages, выбирает актуальную версию и позволяет командам находить запись вне базового snapshot. Это не решает доступность ещё не загруженных страниц — TD-07 имеет другую причину.
- Медленный минутный перебор timezone и лишние расчёты dueAt из прошлых P1 устранены; текущие PostgreSQL tests проходят.
- Fastify/proxy trust обновлены; оба свежих npm audit не обнаружили advisories.
- Android использует защищённое auth storage, iOS — Keychain; старое утверждение о хранении всех токенов в обычных preferences неактуально. TD-04 касается отсутствующего API ротации.
- Logout очищает IndexedDB и auth-состояние; TD-14 касается отдельного native snapshot виджета.
- Напоминания уже имеют retry/expiry/terminal/stale-claim механизмы. Проблема TD-13 — конкретный сброс claim, а не полное отсутствие механизмов доставки.
- Последние изменения уборки и AI уже разделяют текущую просрочку и задачи рассматриваемого периода. Прежнее смешение cleaning backlog в AI не объявляется текущим дефектом.
- Task-event polling имеет ограничения видимости и single-flight. Цикл запросов/причина production 429 этим аудитом не установлены.
- `minimumVersion: null` в форме заботы — намеренное удаление старого продуктового варианта из UI, не поле optimistic locking; `expectedVersion` передаётся отдельно. Это не новый доказанный lost-update bug.

## Порядок работ и критерии завершения

1. **Сохранность и контекст:** TD-01, TD-05, TD-06; добавить воспроизводящие тесты до изменения реализации. Для существующей истории сначала выяснить наличие уже утраченных деталей и доступность backup, без автоматического восстановления поверх новых данных.
2. **Регулярность и доступ:** TD-02/03/13 единым набором инвариантов расписание → occurrence → reminder; TD-04 отдельным iOS bridge изменением. Закрытие требует проверки без открытых клиентов и на настоящем native bridge.
3. **Достоверность экранов:** TD-07…12. Каждый диапазон, счётчик и сводка имеют определённую полноту, дату и состав статусов; ошибки источников не маскируются пустотой.
4. **Lifecycle и платформа:** TD-14 и native часть TD-17; сценарии logout/late response/cold start на обеих платформах. TD-15 исправить небольшим отдельным изменением bootstrap/error mapping.
5. **Сопровождение:** TD-16…19 — контрактные gaps, границы тестов, измерение SQL/bundle/timeout и короткий активный backlog. Рефакторинг выполнять по одному ответственному модулю, с сохранением сценарных тестов.
6. **Продуктовые улучшения:** сначала deep links и Undo, затем политика переносов/дневного ресурса; onboarding и завершение дня проверять на реальном использовании.

Не требуется переписывать приложение целиком. Наибольшую пользу принесут несколько чётких контрактов: история неизменна после редактирования шаблона; будущий план соответствует выбранной области изменения; напоминание не зависит от чтения UI; подтверждение относится к исходному пространству; ошибка независимой команды не останавливает остальные; частичная информация не выдаётся за полную.
