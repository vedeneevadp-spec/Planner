## Подтверждённые проблемы

### R1 · P2 · Успешно сохранённая задача остаётся в конфликте после потери ответа

**Сценарий:** переименовать задачу; сервер сохраняет изменение, но соединение обрывается до получения подтверждения; перезагрузить приложение.

**Фактический результат:** сервер уже содержит новое название и версию `2`, однако очередь повторяет тот же PATCH с `expectedVersion: 1`. Получает HTTP 409 `task_version_conflict` и показывает «Несинхронизированные изменения (1)». Конкурирующего редактирования в воспроизведении не было. Пользователю предлагается вручную сверять данные, хотя его изменение уже применено.

Доказательства:

- В управляемом воспроизведении перехвачен успешный ответ HTTP 200 **после реального сохранения в PostgreSQL**, затем ответ намеренно потерян через `connectionreset`. Повтор после reload вернул 409; отдельный GET подтвердил сохранённое название и версию `2`.
- Первоначально похожее состояние возникло при быстрой перезагрузке после закрытия редактора. Управляемая потеря ответа подтвердила причину независимо от этого первого наблюдения.
- [Запросы, ответы и состояние записи](</Users/daryavedeneeva/ Projects  /Planner/tmp/user-scenario-recheck-20260923/ack-loss-repro.json>), [скриншот конфликта](</Users/daryavedeneeva/ Projects  /Planner/tmp/user-scenario-recheck-20260923/ack-loss-conflict-detail.png>), [скрипт воспроизведения](</Users/daryavedeneeva/ Projects  /Planner/tmp/user-scenario-recheck-20260923/ack-loss-repro.mjs>).

Причина: обычный `task.update` повторяется с прежней ожидаемой версией без распознавания уже применённой команды — [offline-planner-sync.ts:238](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/lib/offline-planner-sync.ts:238>). Терминальная ошибка переводит запись в конфликт — [offline-planner-sync.ts:151](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/lib/offline-planner-sync.ts:151>). Специальное согласование после потери подтверждения есть для следующего этапа задачи, но не для обычного редактирования.

**Последствия:** лишнее ручное восстановление очереди; по логике очереди связанные изменения ожидают разрешения конфликта. Потери уже сохранённого переименования в проверке не произошло. В раскрытом сообщении дополнительно видны технический UUID и английская серверная ошибка, затрудняющие понимание.

**Исправление:** устойчивый идентификатор команды и повторяемый серверный результат либо осторожное распознавание уже применённой операции. Нельзя просто повторять PATCH с новой версией: это может затереть реальное изменение с другого устройства.

**Приёмка:** потеря ответа после commit → reload/reconnect → очередь очищается без ручного действия, запись изменена ровно один раз; настоящий конфликт двух клиентов по-прежнему сохраняет оба варианта и требует разрешения. Проверить отдельно редактирование, статус и перенос даты: последние два здесь отмечены как соседний риск, а не как воспроизведённые дефекты.

### R2 · P2 · Плашка конфликта перекрывает меню другой задачи

**Сценарий:** оставить одну конфликтную операцию, открыть в недельном календаре карточку независимой задачи и её меню на экране 390 × 844 или 320 × 844.

**Фактический результат:** плашка «Несинхронизированные изменения (1)» лежит поверх пункта «Редактировать». Нажатие перехватывает плашка; обычный click по пункту меню невозможен. Проблема затрагивает и задачу, у которой нет конфликта.

Подтверждено на обеих ширинах: `elementFromPoint` в центре пункта возвращает `SUMMARY` плашки; Playwright сообщает `intercepts pointer events`. [390 px](</Users/daryavedeneeva/ Projects  /Planner/tmp/user-scenario-recheck-20260923/conflict-menu-390.png>), [320 px](</Users/daryavedeneeva/ Projects  /Planner/tmp/user-scenario-recheck-20260923/conflict-menu-320.png>), [измерения и результат клика](</Users/daryavedeneeva/ Projects  /Planner/tmp/user-scenario-recheck-20260923/ack-loss-repro.json>).

Причина: фиксированная панель имеет `z-index: 120` — [PlannerOfflineConflicts.module.css:5](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/ui/PlannerOfflineConflicts.module.css:5>), а модальная карточка календаря — `z-index: 80` — [CalendarPage.module.css:1102](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/pages/calendar/ui/CalendarPage.module.css:1102>).

**Исправление:** согласовать слои уведомлений и модальных окон; панель не должна перекрывать действия открытой карточки. Сохранить доступ к разрешению конфликта после закрытия модального окна.

**Приёмка:** при существующем конфликте меню, редактирование и сохранение независимой задачи доступны на 320/390 px; клавиатурная навигация остаётся внутри активного модального окна. Проверить также раскрытую панель конфликта.
