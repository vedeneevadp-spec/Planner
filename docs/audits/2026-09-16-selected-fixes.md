### История и расписание

Миграция `20260916_000103_self_care_history_and_schedule_origin.sql` добавляет мягкое удаление шагов и снимки названия/порядка в их завершениях. Существующие данные заполняются из сохранившихся шагов. Уже уничтоженную старым каскадом историю эта миграция восстановить не может.

`generated_at = null` обозначает ручное расписание или исключение. Миграция распознаёт старые ручные записи по сохранённым деталям расписания. Пересчёт начинается с сегодняшней даты и ограничен ранее созданным горизонтом; последующие даты создаются существующим механизмом чтения или новым фоновым обработчиком. Блокировки записей заботы не позволяют параллельной генерации вернуть старое правило после его изменения.

### Фоновые напоминания

- Горизонт — 31 локальный день: он покрывает максимальное опережение напоминания 30 дней, включая смену часового пояса при DST.
- У каждого правила есть сохраняемая отметка проверки. Обычная повторная генерация выполняется через 6 часов; изменение заботы, правила, курса или значимого завершения делает правило доступным для проверки раньше.
- За один опрос обрабатываются пакеты по 100 правил, максимум 20 пакетов или 10 секунд между пакетами. Затем продолжается обычная доставка. Правила с далёкой датой начала не занимают текущую очередь генерации.
- Заблокированные другим обработчиком записи пропускаются. Ошибка данных одного правила откатывается отдельно, попадает в журнал и повторяется после интервала либо редактирования. Ошибки соединения, прав или транзакции передаются механизму восстановления обработчика.
- Сохраняются действующие правила пауз курсов, ручных исключений и видов заботы, для которых новое посещение планируется вручную после завершения.

Миграция `20260916_000104_self_care_reminder_generation.sql` создаёт служебную таблицу прогресса. У неё включён RLS и отсутствуют прямые права `authenticated`; для существующего `planner_backup` предусмотрен доступ чтения. Используется существующее подключение maintenance worker. Этот прогресс не входит в персональный экспорт и безопасно создаётся заново после восстановления.

### Офлайн-очередь

Проверены отказы `task_status_forbidden`, `task_confirmation_required`, `task_manage_forbidden`, конфликты версий, зависимость от создания сферы и цепочка следующих этапов. Ошибки авторизации, доступа ко всему пространству, 408, 429 и серверные ошибки сохраняют путь восстановления, а не становятся постоянным отказом отдельной команды.

Повтор сохраняет исходный ввод, UUID операции, порядок и ожидаемую версию. Конфликт версий не разрешается автоматической перезаписью: пользователь может сверить сохранённый ввод с текущими данными. Удаление всей связанной группы требует подтверждения. Дополнительный интерфейс и код повторной отправки загружаются отдельно, чтобы сохранить бюджет начального JavaScript.

## TD-10: варианты решения

Сейчас `getTaskResource` возвращает ноль при отсутствии оценки, и антиперегруз делает уверенный вывод по неполным данным. Нужны отдельные состояния «оценки нет» и «оценено как нейтральное».

| Вариант                                              | Поведение                                                                                                                                                                       | Преимущество                                                                                | Цена и ограничения                                                                               |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **1. Показывать полноту оценок — рекомендую первым** | «Оценено 3 из 12 дел. Нагрузка известных дел: 5 из 8; ещё 9 без оценки». Для полностью неизвестного плана — «Нагрузка пока неизвестна».                                         | Небольшое изменение, без дополнительного обязательного ввода; устраняет ложную уверенность. | Не оценивает неизвестные дела за пользователя.                                                   |
| 2. Предлагать приблизительный ресурс                 | Предложение по длительности или шаблону, явно помеченное как приблизительное; пользователь принимает или меняет его.                                                            | Быстрее заполняется план и становятся полезнее предложения разгрузки.                       | Длительность и расход энергии не эквивалентны; непроверенную оценку нельзя представлять точной.  |
| 3. Общий бюджет дня                                  | Учитываются задачи, заботы и уборка; покупки объединяются в одну поездку или сессию, календарное отражение задачи не считается повторно. Сохраняется показатель полноты данных. | Оценка ближе к реальному дню.                                                               | Нужны согласованные правила стоимости, восстановления и устранения дублей; более крупная задача. |
| 4. Ручной бюджет без автоматического вердикта        | Пользователь задаёт доступный ресурс и сам выбирает план; интерфейс показывает оценённый расход и восстановление без «реалистично».                                             | Больше контроля, меньше ложных выводов алгоритма.                                           | Больше ручной работы и меньше помощи при планировании.                                           |

Для варианта 1 предлагаю следующие критерии приёмки:

1. 12 задач без ресурса показывают «Оценено 0 из 12. Нагрузка пока неизвестна», а не «спокойно».
2. `null` и явно выбранный `0` различаются; ввод оценки остаётся необязательным.
3. При частичной оценке не показывается безусловное «план реалистичен». Если даже оценённая часть превышает бюджет, это видно вместе с оговоркой о неполных данных.
4. Ясно указано, какие виды дел входят в расчёт. Ошибка загрузки любого включённого источника помечает расчёт как неполный.
5. После заполнения всех оценок возвращается обычный индикатор. Варианты 2 и 3 можно добавлять позднее, сохраняя различие ручных и приблизительных оценок.

## Дополнительная находка TD-20: коллизия личного пространства при одновременной регистрации

**P2, подтверждено кодом, журналом API и тестовой БД.** В `apps/api/src/modules/session/session.repository.postgres.ts:1483` slug строится из первых 12 hex-символов UUIDv7. Это timestamp в миллисекундах: два разных пользователя, созданных в одну миллисекунду, получают одинаковый slug.

В итоговом E2E два разных actor UUID начинались с `01a0a969-d9d5`. Пространство `personal-01a0a969d9d5` принадлежало первому пользователю, у второго пространства не было. `session_provision_personal_workspace` выполняет `ON CONFLICT (slug) DO NOTHING`, а затем ищет пространство того же владельца; для второго пользователя результат пустой и `/session` возвращает 500 `Failed to provision a personal workspace`.

Это отдельная причина от TD-15 про выбор первого owner. Новый пользователь при одиночном повторе успешно прошёл весь сценарий Today; повтор входа затронутого коллизией пользователя сам проблему не исправляет. Код регистрации не входит в текущие пять исправлений и не изменялся.

Предлагаемое исправление: строить slug по полному UUID либо гарантированно уникальной части, сохраняя существующие slug; атомарно создавать пространство. Приёмка: два UUIDv7 с одинаковыми первыми 12 hex-символами успешно получают разные личные пространства, повтор provisioning каждого возвращает его прежнее пространство.
