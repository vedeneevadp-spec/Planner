### TD-21 · P1 · Привилегированное восстановление может записать данные в чужой ритуал

**SQL/API + CODE, подтверждено на двух искусственных пользователях.** Валидация архива проверяет заявленных владельцев и ссылки внутри самого файла, но не сверяет принадлежность уже существующих идентификаторов с БД. Привилегированное восстановление затем ищет существующие записи только по ID и считает найденную запись допустимой для `kept`.

Доказанный результат: архив пользователя A прошёл проверку без предупреждений (`canRestore=true`), существующий ритуал B был отмечен как `kept`, а новая дочерняя запись попала в ритуал B. Обычный репозиторий с RLS не давал A прочитать этот ритуал; пользователь B увидел добавленный тестовый шаг. **Для воспроизведения требовалось знать UUID ритуала B.** Возможность получить неизвестные UUID, массовое чтение чужих данных или инцидент в production не установлены.

Причина: [валидация архива](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/backups/backup.service.ts:135>), [restore без пользовательского RLS-контекста](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/backups/backup.repository.postgres.restore.ts:131>), [поиск существующих ID без scope](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/backups/backup.repository.postgres.restore.ts:562>). Внутренний [helper повторяет ту же валидацию](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/backups/backup.restore-helper.ts:210>), поэтому проверка подписи внутреннего запроса не заменяет проверку владельца записей. Сетевой production-helper не тестировался; runtime-доказательство получено через сервис и привилегированный repository path.

**Исправление:** внутри транзакции до любых изменений проверять фактическое владение всеми существующими ID и всеми родительскими ссылками. Коллизия с чужим объектом должна отклонять весь импорт. Условия scope должны присутствовать и в последующих update/resurrect/deferred-reference операциях; по возможности закрепить соответствие владельцев ограничениями БД.

**Приёмка:** архив A со ссылками на существующие активные/удалённые объекты B отклоняется целиком; ни один объект B и ни один файл не меняется. Валидный импорт A остаётся идемпотентным. Проверить все таблицы восстановления, включая косвенные ссылки, а не только шаги ритуалов.

### TD-22 · P1 · Редактирование начатого ритуала сбрасывает отмеченные шаги

**SQL/API + CODE.** Общая форма повторно отправляет весь список шагов [без прежних ID](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/pages/self-care/ui/SelfCarePage.form-model.ts:821>). Сервер при наличии `steps` вызывает замену и [безусловно удаляет все drafts ритуала](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care/self-care.repository.postgres.ts:2514>). Это происходит до [пересогласования расписания](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care/self-care.repository.postgres.ts:524>).

Доказанный сценарий: отметить шаг будущего автоматического повторения → через payload общей формы изменить правило с ежедневного на еженедельное. Draft исчезает (`1 → 0`); повторение, ранее защищённое наличием draft, тоже удаляется. Сброс отметок происходит и при замене шагов без изменения их содержания; сохранение одного названия через форму также отправляет `steps`. **Завершённые записи истории в этом сценарии сохраняются.**

**Исправление:** сохранять ID шагов, отправлять только изменённые поля и согласовывать drafts по устойчивым ID. Изменение названия не должно заменять структуру. При настоящем удалении отмеченного шага нужна определённая политика сохранения/подтверждения прогресса. Пересогласование расписания должно видеть исходные защищённые повторения.

**Приёмка:** начатый ритуал → rename; изменение текста/порядка шага; изменение расписания; offline replay. Неизменённые отметки и защищённые повторения сохраняются, завершённые снимки не переписываются.

### TD-23 · P2 · Резервная копия не возвращает ранее удалённый шаг

**SQL/API + CODE; граница после TD-01.** Новая миграция использует soft delete шагов, но [restore policy](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/backups/backup.repository.postgres.restore.ts:68>) не помечает `self_care_ritual_steps` как таблицу с `deleted_at`. Поэтому tombstone считается обычной сохранённой записью, и [ветка восстановления](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/backups/backup.repository.postgres.restore.ts:527>) не выполняется.

Доказательство: backup ритуала из двух шагов → удалить один → восстановить backup. Активных шагов остаётся один, `deleted_at` старого шага сохраняется, `resurrected=0`. Проверка восстановления после физического удаления всего ритуала этот случай не покрывает.

**Исправление/приёмка:** синхронизировать политику restore с soft delete и проверить цикл export → удалить отдельный шаг → restore: шаг возвращается с прежним ID, история не теряется, повторный restore не создаёт дублей. Сначала исправить изоляцию TD-21.

### TD-24 · P2 · Расписание без timezone зависит от того, кто первым создал повторение

**SQL/API + CODE; неполный край TD-03.** Допустимое правило с `timezone=null` интерактивно использует [часовой пояс клиента](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care/self-care.repository.postgres.ts:723>), а [фоновый генератор выбирает UTC](</Users/daryavedeneeva/ Projects  /Planner/apps/api/src/modules/self-care-reminders/self-care-reminders.occurrence-generator.ts:149>).

Для одного правила `09:00` чтение с `Asia/Novosibirsk` создало `02:00Z`, а фон — `09:00Z` следующего дня: разница семь часов. В fixture профиль имел UTC; поэтому здесь **не утверждается, что Novosibirsk обязательно правильнее**. Дефект — отсутствие единой сохранённой политики для одинакового правила. Реальная распространённость старых NULL-правил не измерялась.

**Исправление/приёмка:** определить приоритет rule → сохранённый пользовательский/workspace timezone и закреплять effective timezone при создании/миграции. Интерактивный путь и worker должны получать одинаковый `dueAt` независимо от порядка чтения, отсутствующего заголовка и перезапуска. Отдельно проверить смену пользовательской зоны и DST.

### TD-25 · P2 · Повтор уже принятой правки конфликтует с ней самой

**DIAG + реальный HTTP на временной БД.** [HTTP и обновление кэша](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/lib/offline-planner-sync.ts:130>) происходят до отдельного удаления durable-команды. При потере ответа или прерывании между этими действиями обычный `task.update` повторяется с прежней `expectedVersion`. Сервер уже имеет v2 и отвечает 409 на expected v1.

Диагностика текущего drain и fake IndexedDB: первая правка записана на сервер; replay даёт `task_version_conflict`, следующая команда той же задачи — `dependency_blocked`; независимая задача успешно выполнена. [«Повторить»](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/lib/offline-planner-conflicts.ts:104>) сохраняет ту же старую версию и возвращает тот же конфликт. Payload не потерян, но автоматического продолжения нет. Для schedule аналогичный путь подтверждён кодом; физическое убийство браузера не выполнялось.

**Исправление/приёмка:** стабильный command ID и сохранённый результат применения либо надёжное подтверждение результата конкретной операции. Lost response и прерывание после commit должны приводить к подтверждению уже выполненной команды и продолжению зависимых. Реальная чужая правка должна оставаться конфликтом; простая подстановка свежей версии недопустима. Create, same-status и next-stage имеют отдельные защиты — эта находка не относится ко всем командам подряд.

### TD-26 · P2 · Успешное чтение сервера перезаписывает ожидающую локальную правку

**DIAG + HTTP + CODE.** [Query сохраняет и возвращает сырой server snapshot](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/model/planner-queries.ts:163>); [IndexedDB заменяет записи пространства](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/lib/offline-planner-store.ts:627>) без наложения ожидающей очереди.

Доказательство: offline edit M1 создаёт локальную title/v2 → до replay приходит GET серверной title/v1 → кеш снова содержит v1 → M2 создаётся по этой версии. Replay M1 переводит сервер в v2, M2 получает ложный 409. Чужого изменения не было. Запись остаётся в очереди, но пользователь временно видит старую задачу. Android [personal read для виджета](</Users/daryavedeneeva/ Projects  /Planner/apps/web/src/features/planner/ui/NativePlannerWidgetSync.tsx:720>) также пишет в общий кеш; это дополнительная ветка той же причины, проверенная только кодом.

**Исправление/приёмка:** отделить серверный снимок от локальной проекции либо применять ordered pending-команды при чтении, persistence и hydration. M1 → GET старой версии → M2 → reconnect сохраняет обе правки без ложного конфликта; pending create/update/delete не исчезают с экрана после refetch. Проверить несколько вкладок, смену workspace и настоящий внешний конфликт.

Три продуктовых улучшения, **не дополнительные подтверждённые баги**:

1. **Объяснять предложения разгрузки.** Сейчас ранжирование может поставить обязательную срочную задачу со сроком сегодня перед лёгкой необязательной. Сохранять ручной выбор, но показывать причину рекомендации и срок; рассмотреть режим «сначала необязательные». Не запрещать перенос важных дел автоматически. Приёмка: пользователь понимает основание и видит последствия выбора.
2. **Сделать период истории явным.** История/общая аналитика заботы используют последние 30 дней, подробные тренды — другой диапазон. Показывать период, «за этот период записей нет» и переход к более ранним записям; не загружать всю историю сразу. Особенно полезно для редких процедур и измерений.
3. **Согласовать восстановление после быстрых действий.** Где отмена допустима, давать её рядом с результатом; после переноса уборки сразу показывать новую дату. Доступность undo цепочки сейчас различается между durable-queue и прямым fallback. Отмена должна учитывать синхронизацию и последующие чужие изменения, а не обещать безусловный откат.

Общий продуктовый принцип: в каждом разделе различать **факт / план / архив**, **данные полны / частичны / устарели**, **изменение принято сервером / ожидает / конфликтует**. Тогда экраны становятся предсказуемыми без добавления новых сущностей и обязательных форм.
