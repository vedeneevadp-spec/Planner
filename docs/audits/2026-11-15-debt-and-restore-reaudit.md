# Техдолг и серверная защита восстановления: повторный аудит

Дата: 15 ноября 2026 года. Ветка `codex/audit-remediation-20261115`, база
`6a6a9d7638846f76f0122e82b9ceab25144e5c19`. Результат относится к локальному
рабочему дереву, без deployment, публикации приложений и изменения пользовательской БД.

Продолжение [исправлений A01–A14](2026-11-15-remediation-reaudit.md).
Устранены оставшиеся конкретные риски серверного порядка записей и уборки файлов,
убрана старая реализация habits из рабочего интерфейса, разделены крупные модули,
ограничен поиск в PostgreSQL и уменьшена начальная загрузка. Новых production
зависимостей нет. Размер файла сам по себе не используется как критерий дефекта.

## Защита восстановленных данных

Миграция `20261115_000119_workspace_write_epochs.sql` хранит поколение пространства
отдельно от пользовательского архива. Restore проверяет ожидаемое поколение и
увеличивает его в одной транзакции с восстановлением. Повтор idempotency key
возвращает прежний результат; rollback не меняет поколение.

- PostgreSQL согласует записи и restore через общий advisory lock. Триггеры
  охватывают восстановленные domain-таблицы, профиль и журналы команд. Старое
  поколение отвергается как `409 workspace_restored`; runtime не может менять
  coordination metadata.
- API берёт блокировку до блокировок строк. Прямые RPC/интеграции, дошедшие до
  row trigger во время restore, получают конфликт сразу, без ожидания и deadlock.
  Записывающие транзакции требуют READ COMMITTED. Привилегированное обслуживание
  без пользовательских claims сохраняется для owner/BYPASSRLS роли.
- Свежий `/api/v1/session` возвращает поколение в заголовках. Чтение повторяется,
  если restore завершился во время загрузки: старый кэш профиля не маркируется
  новым поколением. Для переноса задач и редактирования профиля передаются поколения
  выбранного и личного пространств. Web привязывает список областей к пользователю;
  фиксируется вся карта, обновление любой области пересоздаёт клиент. Заголовки
  разрешены в CORS и не заменяют авторизацию.
- Web requester фиксирует поколение при создании; offline-команды — до первого
  ожидания IndexedDB. Старые команды нельзя автоматически перемаркировать после
  обновления сессии, очистки storage или смены клиента. Новые действия используют
  обновлённый API-клиент.
- Android-виджет и действия уведомлений сохраняют исходное поколение. Устаревшие
  pending completion IDs не попадают в новую проекцию. Push содержит поколение,
  прочитанное при получении reminder обработчиком.
- API keys, Алиса и MCP используют первоначальное время ключа, сессии или OAuth
  grant. Refresh не обновляет это доказательство: у Алисы используется подписанный
  UUIDv7 session ID, у MCP сохраняется исходный `created_at`. Выдача credentials
  также синхронизирована с restore. Старые интеграции требуют нового ключа или
  повторной авторизации перед новыми записями.

Проверены фактическое ожидание блокировки, задержанный запрос, немаркированный
старый клиент, rollback, replay, изоляция другого пространства, позднее изменение
профиля, старые/новые credentials, запрет изменения metadata, concurrent issuance,
работа отдельной maintenance-роли и отсутствие deadlock у прямого RPC.

## Исправления, найденные при повторном разборе

1. Неопределённый результат commit при restore больше не удаляет подготовленный
   аватар. Неиспользуемый файл остаётся кандидатом для последующей безопасной GC.
2. Исправлена выдача нового поколения вместе с кэшированным профилем и сохранение
   старого API-клиента после обновления сессии. Проверено в настоящем Chromium.
3. Убрана возможность присвоить новой записью в IndexedDB новое поколение уже
   начатой команды. Добавлена регрессия с изменением epoch во время enqueue.
4. Закрыты обход через свежий JWT `iat` Алисы, выдача credentials посреди restore,
   deadlock прямого RPC и несовместимость trigger с отдельной maintenance-ролью.
5. GC теперь требует полного доступа к ссылкам, а deploy-проверка restore role
   учитывает новую таблицу metadata.
6. После разделения вкладок заботы найден и исправлен offline-переход на план:
   его код загружается до открытия формы, поскольку сохранение запланированного
   дела может переключить вкладку уже без сети.
7. После личного restore свежие переносы задач и правки профиля из общего
   пространства проходят с картой актуальных поколений; старые — получают 409.
   Добавлены HTTP/браузерные проверки и проверка пересоздания клиента при смене
   поколения дополнительной области без изменения объекта сессии.
8. Алиса сообщает о необходимости проверить восстановленные данные и заново
   связать аккаунт; конфликт больше не превращается в предложение повторить
   старую команду.
9. Повторная проверка подключений перед GC сбрасывает статистический snapshot
   PostgreSQL. Регрессия с двумя настоящими соединениями подтверждает, что новое
   подключение обнаруживается, хотя обычное повторное чтение его ещё не видит.
10. Поздний ответ Android bridge и переход между командами проверяют исходное
    поколение до отправки. Обработка сохраняет исходный API-контекст, отложенные
    команды разделены по actor/workspace/epoch, ACK содержит поколение. Native
    чтение очереди и её поколения атомарно относительно записи конфигурации;
    старый ACK не удаляет новую команду с тем же task ID.
11. В Gradle приложения убран неявный поиск версий в родительском проекте:
    используются явные `rootProject.ext` ссылки без изменения самих версий.
12. E2E восстановления пароля получает уникальный email на каждый запуск.
    Повторное использование фиксированного адреса накопило серверную квоту и
    дало ожидаемый 429; лимит защиты приложения сохранён.

## Выпуск и границы подтверждения

Для этого рабочего дерева нужны миграции `000115`–`000119` и согласованное
обновление API, web и native bundle. Клиенты без `x-workspace-epoch` считаются
поколением `0` и после первого restore не смогут записывать восстановленные
данные. Старые API keys/OAuth grants нужно заменить или повторно авторизовать;
старые команды с новыми credentials автоматически не повторяются.

Restore role должна иметь `SELECT,INSERT,UPDATE` на `workspace_write_epochs`.
Worker требует `EXECUTE` на `read_workspace_write_epoch(uuid, uuid)`.
Инструкции: [user backups](../user-backups.md), [GC runbook](../disaster-recovery.md),
[public API](../public-api.md), [миграции и выпуск](../release-workflow.md).

Полный инфраструктурный rollback БД — отдельная процедура: он возвращает также
coordination metadata. До открытия записи после такого отката нужно инвалидировать
прежние сессии/ключи и очереди. Автоматический откат приложения на версию без epoch
после пользовательского restore несовместим с новой защитой.

Повторная полная iOS-сборка по-прежнему останавливается до компиляции приложения:
Xcode не может загрузить IDESimulatorFoundation из-за несовместимого DVTDownloads.
Swift regression runner проходит. Физические устройства и выполнение Android
instrumentation на устройстве не проверялись. Production, удалённый CI, внешние
SMTP/FCM/OAuth, offsite storage и реальное аварийное восстановление не изменялись
и не объявляются проверенными этим локальным аудитом.

Остаются внешние предупреждения совместимости Gradle из AGP/Capacitor и
генерируемого Cordova script (`Configuration.setVisible`, неявный поиск parent
properties). Сборка на закреплённом Gradle 9.8.2 проходит; переход на Gradle 10/11
потребует совместимых версий этих плагинов. Исходники `node_modules` и
генерируемые файлы не патчились для сокрытия предупреждений.

Одноразовый контейнер `planner-debt-20261115` удалён после проверки. Порты
тестовых API, restore-helper, web server и PostgreSQL закрыты; результаты
сохранены в `cleanup.log` и `cleanup-ports.json`. Изменения остаются в рабочем
дереве; commit, push и deployment не выполнялись.
