# Аудит технического долга Planner / Chaotika

Дата: 6 сентября 2026. Проверенный commit: `a2b8efcc0540727204dd7a2330ae141d92e373fe`.

Главный вывод: базовые проверки проекта работают, но они пропускают ошибки на границе общего кэша задач и новых постраничных выборок. Кроме того, обнаружены дорогой синхронный алгоритм преобразования времени и актуальные advisories зависимостей, блокирующие полный CI gate. Приоритет — исправить эти конкретные проблемы, затем укрепить проверки соответствующих сценариев.

Выделено **4 пункта P1, 6 пунктов P2 и 1 пункт P3**. P0 по собранным данным не установлен. P1 — ближайший цикл исправлений; P2 — плановый долг с конкретными последствиями; P3 — сопровождение документации. Это приоритет работ по проекту, а не шкала CVSS.

## Находки

### TD-01 · P1 · Dependency audit блокирует CI; обновление Fastify требует изменения proxy-контракта

**Подтверждение.** В lockfile установлены `fastify@5.9.0`, `fast-uri@3.1.5`. Свежий `audit:prod` обнаружил четыре high advisory для fast-uri и два moderate для Fastify; npm агрегирует их в две затронутые зависимости. [Полный JSON](../../tmp/tech-debt-audit-2026-09-06/npm-audit-prod.json), [результат штатного gate](../../tmp/tech-debt-audit-2026-09-06/audit-prod-online.log).

Для Fastify существенен код `apps/api/src/bootstrap/build-app.ts:145`: `trustProxy: config.trustedProxyHops`. В `.env.production.example:10` используется значение `1`. По [advisory разработчиков](https://github.com/fastify/fastify/security/advisories/GHSA-3m5p-2c4r-xxw2) исправление в 5.12.1 исключает числовую форму `trustProxy`; требуется политика, проверяющая адрес доверенного прокси. Поэтому одного пересчёта lockfile может быть недостаточно.

Для fast-uri исправлена ветка 3.1.6; условие одной из проблем — нормализация недоверенного URL перед исходящим запросом или проверкой host. [Advisory разработчиков](https://github.com/fastify/fast-uri/security/advisories/GHSA-f65p-4m7j-42xc).

**Граница вывода.** Уязвимая версия и отказ gate подтверждены. Реальная SSRF или обход proxy на production не доказаны: приложение непосредственно fast-uri не импортирует, а production example привязывает API к loopback. Для другого Fastify advisory проект во многих маршрутах дополнительно валидирует данные Zod; нельзя автоматически объявлять их уязвимыми.

**Исправление.** Отдельный dependency PR: проверить актуальный безопасный релиз Fastify, обновить транзитивный fast-uri и затронутые dev packages, перевести proxy configuration с количества hops на разрешённые адреса/сети. Согласовать Caddy и тестовые forwarded headers. Не отключать audit gate и не расширять исключения ради зелёного CI.

**Приёмка.** Оба audit gate проходят; запрос от недоверенного адреса не меняет trusted host/protocol/IP; запрос через разрешённый прокси работает; auth/OAuth/MCP rate-limit tests и smoke проходят. Production-origin reachability проверяется отдельно при выпуске.

### TD-02 · P1 · Преобразование времени синхронно перебирает 36 часов по минутам

**Причина.** `packages/contracts/src/time/time.service.ts:381` задаёт диапазон ±18 часов; цикл на строке 386 проверяет 2 161 минутную позицию. `getZonedDateTimeParts` на строке 416 каждый раз создаёт новый `Intl.DateTimeFormat`. Нормализация зоны добавляет ещё один formatter на преобразование.

**Воспроизведение без БД.** Прямой вызов текущего `makeFixedZoneDateTime`, Node 24.19.0, `Asia/Novosibirsk`, 09:00:

| Преобразований | Создано Intl.DateTimeFormat | Время одного прогона |
| -------------: | --------------------------: | -------------------: |
|              1 |                       2 162 |             96,88 мс |
|             31 |                      67 022 |          2 595,84 мс |

[Измерения](../../tmp/tech-debt-audit-2026-09-06/time-conversion-metrics.json), [скрипт](../../tmp/tech-debt-audit-2026-09-06/measure-time-conversion.mts). Это синхронная работа JS: на сервере она удерживает event loop. Значения зависят от машины; алгоритмический перебор подтверждён кодом и счётчиком конструкторов.

**Пользовательский путь.** `self-care.shared.ts:713` создаёт occurrences через этот helper. `self-care.repository.postgres.ts:747` и `:762` вызывают генерацию при чтении dashboard/плана. Затем `:728` заново вычисляет dueAt для каждого occurrence через отдельный SQL `make_timestamptz` (`:2247`). Работа выполняется дважды в разных реализациях.

План одной ежедневной привычки с preferredTime на новый месяц локально занимал 2,43–2,86 с; повторное чтение готового месяца — 30 мс. SQL-профиль подтверждает 28–31 отдельных time-conversion запросов. Но эти SQL-преобразования суммарно заняли лишь 37–46 мс: основную задержку нельзя приписать N+1. Изолированный JS-замер показывает дорогую CPU-часть. [Профиль](../../tmp/tech-debt-audit-2026-09-06/self-care-generation-metrics.json).

**Исправление.** Сначала переиспользовать formatter и заменить минутный перебор ограниченным поиском offsets с сохранением принятой DST-политики; затем устранить повторный расчёт dueAt и пакетировать оставшуюся SQL-работу. Отделить обеспечение occurrences от сборки read model так, чтобы стоимость первого чтения была явной и контролируемой.

**Приёмка.** Сохраняются результаты на DST gap/fold, неоднозначном локальном времени и смещениях на 30/45 минут; проверяются timezone contracts. Количество formatter constructions больше не растёт как `2162 × occurrences`. Добавлен воспроизводимый performance budget на генерацию 31/365 occurrences. Конкретный SLA закрепляется после измерения целевого runtime.

### TD-03 · P1 · Календарный кэш перекрывает свежие изменения старой записью

**Причина.** Общий ключ: `['planner','tasks',workspaceId,sessionVersion]` (`planner-queries.ts:78`). Курсорный: `['planner','tasks','cursor',workspaceId,filters]` (`usePlannerTaskCursor.ts:29`). Мутации инвалидируют первый ключ (`planner-mutations.ts:393`), как и обычная обработка task events (`planner-offline.ts:225`). Курсорный ключ не является его дочерним ключом.

Календарь сначала кладёт в Map общий список, затем без сравнения версий перезаписывает его cursor items (`CalendarPage.tsx:721`). В результате свежая общая запись может быть перекрыта старой календарной.

**Воспроизведение.** Изолированный тест исполняет реальный `usePlannerMutations.updateTaskMutation`, подменяя только HTTP-ответ. После успеха: snapshot title `After`, snapshot invalidated `true`, cursor title `Before`, cursor invalidated `false`; объединение по алгоритму календаря даёт `Before`. [Результат](../../tmp/tech-debt-audit-2026-09-06/cursor-cache-result.json), [тест](../../tmp/tech-debt-audit-2026-09-06/cursor-cache.test.mts).

Это проверка hook и алгоритма объединения, не отдельный браузерный replay. Основной путь через очередь также обновляет общий ключ; отдельная инвалидация calendar cursor на обычное событие отсутствует. Refocus или ручное обновление может скрыть симптом, но не устраняет несогласованность.

**Исправление.** Единая фабрика ключей с workspace как общим префиксом; все изменения и task events обновляют/инвалидируют зависимые cursor queries. При объединении нужен порядок по версии/updatedAt или единое хранилище записей, а не безусловный приоритет последней выборки.

**Приёмка.** Изменение названия, перенос, удаление и завершение сразу отражаются в календаре; проверяются online queue, fallback mutation, replay и remote task event. Старый refetch не возвращает прежнюю версию.

### TD-04 · P1 · Задача из дополнительной страницы видна, но команды не находят её

**Причина.** `getCachedTaskRecord` (`usePlannerState.ts:392`) ищет только в основном snapshot. `updateTask` (`:612`), `setTaskStatus` (`:975`) и удаление (`:1196`) прекращают выполнение, если записи там нет. Calendar cursor добавляет записи лишь в локальный список страницы (`CalendarPage.tsx:721`); загруженные страницы архива аналогично остаются в своём hook (`useTodayClosedTaskPagination.ts:41`).

**Воспроизведение выборок.** В настоящем TaskService + PostgreSQL созданы 600 активных будущих задач. Основной snapshot возвращает 250 старейших и 250 новейших; задача №300 отсутствует. Calendar cursor возвращает первые 500 и включает №300. Таким образом, интерфейс получает запись, а command layer не получает её version. [Результат](../../tmp/tech-debt-audit-2026-09-06/task-cache-gap-result.json), [скрипт](../../tmp/tech-debt-audit-2026-09-06/reproduce-task-cache-gap.mts).

Отказ UI-команды установлен по её явной проверке в коде; полный клик по такой задаче в браузере отдельно не воспроизводился. Это не основание утверждать потерю данных: команда останавливается до отправки.

**Исправление.** Команды должны разрешать запись независимо от состава summary snapshot: нормализованный entity cache либо получение детали по id с актуальной version. Сохранить optimistic/offline projection и контроль версии. Не возвращаться к неограниченной загрузке всех задач.

**Приёмка.** На наборе >500 active и >100 closed можно изменить, перенести, завершить и удалить запись, которая пришла только из calendar/history cursor. Проверить offline-доступность и запрет записи в чужой workspace.

### TD-05 · P2 · Продолжение active/range выборок не доведено до интерфейса

В `CalendarPage.tsx:711` используется одиночный cursor query с `limit:500`; `nextCursor` не запрашивается. Есть сообщение о частичном диапазоне, но нет загрузки следующей страницы. Infinite cursor подключён к закрытым задачам Today, а не к календарю или active snapshot.

В `TodayPage.tsx:168` сообщение утверждает доступность продолжения active/range через постраничную загрузку, хотя соответствующего пользовательского действия здесь нет. `SpherePage.tsx:52` фильтрует только общий частичный snapshot, поэтому список задач сферы тоже может быть неполным.

**Исправление.** Подключить продолжение для calendar/active views, а для сферы — целевую серверную выборку или честную индикацию границ. Считать показанные и полные данные раздельно; синхронизировать это с TD-04.

**Приёмка.** Достижимы все записи на наборах >500 active/даты; следующие страницы не дублируются; смена диапазона/workspace сбрасывает cursor; сообщение об ограничении сопровождается работающим действием.

**Приёмка.** Versioned performance fixture для 1k/10k задач с query count, payload и latency budget; измеряются UI snapshot, calendar cursor и AI отдельно. Уменьшение стоимости не меняет total/truncated и не теряет incremental events.

### TD-08 · P2 · Часть OpenAPI контрактов остаётся произвольным JSON

**Приёмка.** Required fields, enums, nullable и error responses согласованы с runtime contracts; изменение DTO ломает тест согласованности. Новые placeholders не добавляются незаметно.

### TD-09 · P2 · Native auth gate проверяет симуляцию bridge, но не полный установленный runtime

`mobile-auth-installed.spec.ts:68` использует `page.addInitScript`; далее определяет `window.Capacitor`, nativePromise и storage handlers. Это полезная проверка web lifecycle с native-shaped интерфейсом, но она не исполняет Android Keystore, реальную конкуренцию JS/widget и поведение ОС при остановке процесса.

### TD-10 · P2 · У initial JS почти нет запаса до принятого бюджета

Свежая production build: **800 550 байт initial JS** при лимите **800 768 байт** (`782 × 1024`, `check-web-bundle-budget.mjs:30`). Остаток **218 байт**, около 0,027%. [Размеры initial chunks](../../tmp/tech-debt-audit-2026-09-06/bundle-metrics.json).

Практический долг — почти любое увеличение общего импорта способно блокировать сборку и провоцировать ручное повышение лимита.

**Исправление.** Разобрать состав initial graph, отложить не нужные до открытия маршрута schemas и feature imports, проверить публичные barrel imports. Вернуть обоснованный запас; изменение самого бюджета подтверждать измерением first useful screen на целевом мобильном runtime.

**Приёмка.** Снижение initial bytes и отсутствие новых eager voice/native/lottie imports; измерены старт и переходы, чтобы перенос кода не ухудшил рабочие сценарии.

## Что уже решено и не включено повторно в открытый долг

- Основной planner loader использует bounded read model; календарь имеет range cursor, AI — bounded task read model с coverage. Старого `listTasks({}, signal)` в основном query path больше нет.
- Self-care backend уже имеет отдельный `PostgresSelfCareReadModelLoader`; прежний общий loadState не является актуальной рекомендацией.
- Native auth хранится через secure storage: Android legacy/secure preferences исключены из cloud backup и transfer; iOS использует Keychain с ThisDeviceOnly. Один `allowBackup=true` не доказывает backup токенов.
- PostgreSQL runtime выбирает `PostgresRateLimiter` (`apps/api/src/main.ts:134`); найденный MemoryRateLimiter относится к memory/test path.
- Logout имеет общий cleanup пяти offline stores и межвкладочную invalidation (`session-offline-data-cleanup.ts`). Прежний тезис «logout не чистит IndexedDB» не воспроизводится как описание текущей реализации.
- Репозиторий содержит разделение API/worker/restore/backup principals, JS runtime build, systemd hardening, backup/restore contracts, migration hygiene и PostgreSQL 17 compatibility job. Их фактическое production-состояние в этом аудите не подтверждалось и не объявляется неисправным.
