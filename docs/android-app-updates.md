# Обновления Android внутри Хаотики

Хаотика проверяет новую версию при запуске и возвращении в приложение.
Успешная автоматическая проверка сохраняется на сутки. Без новой версии или
при ошибке автоматической проверки интерфейс остаётся тихим. В «Ещё» доступна
ручная проверка, которая обходит этот интервал.

Предложение «Обновить / Позже» не блокирует планнер. «Позже» скрывает эту версию
на сутки; более новая версия может появиться раньше. APK скачивается только
после нажатия «Обновить», показывает прогресс и хранится в приватном кэше.
После скачивания открывается системный установщик. Android может сначала
попросить разрешить установку из Хаотики. При отказе файл сохраняется для
повторной попытки. Если Android завершит процесс во время скачивания, следующая
попытка начнёт скачивание заново. Скачанный файл переживает закрытие приложения,
но система может очистить кэш при нехватке места.

## Доставка

Новых production-зависимостей нет. Используются Capacitor, Android HTTP API,
существующий FileProvider и Caddy на текущем VPS.

- Манифест: `https://chaotika.ru/android-updates/latest.json`.
- APK: `/android-updates/Chaotika-<version>-build<code>-arm64-v8a.apk`.
- Каталог на сервере: `/var/lib/planner/android-updates`, root-owned, доступен
  Caddy только для чтения. Он сохраняется при обычном deploy и откате кода.
- Отсутствующий манифест (404/204) означает, что доступной версии пока нет.
- Текущий канал APK — arm64. Несовместимые ABI/версии Android не получают
  предложение установить неподходящий APK.

## Проверки перед установкой

Нативный код принимает только известную версию формата и фиксированный origin
Хаотики, без перенаправлений, URL-параметров и сторонних адресов. Размер
ограничен 80 МиБ, манифест — 32 КиБ. Проверяются SHA-256, package id, версия
из APK и совпадение подписантов с установленным приложением. Понижение и
повторная установка текущего versionCode через этот механизм запрещены.
Проверка повторяется перед открытием установщика, включая ранее скачанный APK.
Установку окончательно проверяет и подтверждает Android.

Кнопки не меняют сессию, задачи или очередь синхронизации. Запросы обновления
не используют авторизационные токены пользователя. Скачивание идёт в фоне
процесса приложения; отдельные постоянные уведомления и разрешение на точные
будильники не добавляются.

## Выпуск новой версии

Первый APK с поддержкой обновлений нужно один раз доставить прежним способом.
Установленная 1.1.27 сама обновляться ещё не умеет. При подготовке следующего
публичного APK увеличьте versionCode/versionName по обычному release workflow.

1. Выполнить обычные проверки и production deploy: он добавит маршрут Caddy.
2. Собрать подписанный arm64 APK с текущим ключом подписи.
3. Подготовить короткие пользовательские заметки в UTF-8 файле.
4. Подготовить и проверить артефакты без публикации:

   ```bash
   npm run mobile:update:prepare -- --notes-file=tmp/update-notes.txt
   ```

5. Опубликовать проверенную сборку:

   ```bash
   npm run mobile:update:publish -- --notes-file=tmp/update-notes.txt
   ```

Можно указать `--apk`, `--output` и `--host`. По умолчанию используется
существующий release APK и production SSH host проекта. Нужны Android build
tools и JDK, используемые для сборки APK.

Скрипт проверяет release-подпись, package id, отсутствие debug-флага,
архитектуру, размер и выравнивание. Передача идёт во временный закрытый каталог.
Под блокировкой сервер повторно проверяет размер и SHA-256, запрещает понижение
версии и замену опубликованного build другим APK. Сначала атомарно появляется
APK, затем — новый `latest.json`. Предыдущие файлы остаются доступны для
клиентов, которые начали скачивание до публикации новой версии.

Обновление доступно независимо от публикации сообщения в Telegram; при выпуске
нужно учитывать согласованный с пользователем порядок доставки.

## Проверка перед выпуском

- `npm run test:app-update` проверяет метаданные, подпись и запрет отката в
  скрипте публикации. `mobile:update:prepare` дополнительно проверяет настоящий
  APK через Android build tools, не загружая его на сервер.
- `npm run test:web:run -- AppUpdatesProvider.test.tsx` проверяет тихий запуск,
  ручную проверку, «Позже», прогресс и повторную попытку после ошибки.
- `npx playwright test tests/e2e/android-app-updates.spec.ts --project=chromium`
  проверяет настоящий маршрут «Ещё», светлую и тёмную темы и доступность баннера.
  Для браузерного теста используется штатная изолированная E2E-база; нативный
  мост заменён заглушкой.
- `npm run mobile:android:test` проверяет формат манифеста и адреса загрузки.
- `PlannerAppUpdatesInstrumentedTest` проверяет настоящий HTTP-клиент, кэш,
  отложенное предложение, целостность APK и подписантов на Android. Для сценария
  успешной загрузки нужно дополнительно передать APK с тем же debug-ключом и
  `versionCode` на единицу выше установленной тестовой сборки:

  ```bash
  adb push /path/to/next-debug.apk /data/local/tmp/planner-update.apk
  adb shell am instrument -w \
    -e class ru.chaotika.app.PlannerAppUpdatesInstrumentedTest \
    -e updateApk /data/local/tmp/planner-update.apk \
    ru.chaotika.app.test/androidx.test.runner.AndroidJUnitRunner
  ```

  Без аргумента `updateApk` пропускается только сценарий с настоящим новым APK.
  Отдельно проверьте системные окна: отказ в разрешении, разрешение установки,
  отмену установщика, повторную попытку и сохранение данных после обновления.

Документация Android:
[разрешение установки](<https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()>),
[передача APK через FileProvider](https://developer.android.com/reference/androidx/core/content/FileProvider).
